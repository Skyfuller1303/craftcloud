# ADR-0025: SMTP delivery and verified email ownership

Status: accepted for local AC-09 implementation (2026-10-31). Supersedes ADR-0017 when email delivery is enabled.

## Decision

An optional SMTP transport sends transactional mail through a durable PostgreSQL outbox. With no `CRAFTCLOUD_MAIL_TRANSPORT`, existing invitation and reset link-copy behavior remains unchanged. Configured SMTP requires STARTTLS or implicit TLS with certificate verification, the AC-02 encryption key, and a configured public URL. Relay authentication is optional; username and password-file configuration must appear together. SMTP errors and logs never contain recipients, credentials, message bodies, or link tokens.

The triggering transaction inserts the outbox row. Link capabilities remain hashed in their domain tables; the queue contains only an authenticated encrypted token using the AC-02 key, the outbox UUID as owner, and AAD `email`. Templates are repository text and HTML files with literal escaped substitution, English fallback, and no tracking. Security notices contain no action links.

The worker claims bounded batches using leases and retries transient failures with exponential backoff, at most eight attempts within 24 hours. Permanent failure or exhaustion is audited; successful, failed, and expired messages lose their ciphertext. SMTP and PostgreSQL cannot commit atomically: delivery is at least once, with a stable Message-ID, so a crash after SMTP acceptance can cause a duplicate. Exactly-once delivery is not claimed. Ephemeral verification capabilities and queued mail are excluded from backups so restore does not revive pending email changes or send stale messages.

With delivery enabled, inviters never receive bearer links. Invitations to new addresses create accounts only after mailbox link possession and password selection, marking the address verified. Existing unverified accounts are not silently migrated to verified status. They can request verification; operators can initiate verification for them. Existing unverified accounts must verify before accepting another organization's invitation. Invitation responses do not reveal whether the address already has an account.

Self-service email changes require the current password and, when configured, a current second factor. A single-use confirmation sent to the new address expires after 24 hours; the old address receives a notice without an action link. The account address changes only on confirmation, after current account/security state and uniqueness checks. Tokens appear only in URL fragments and request bodies, never persistent browser storage.

An email-change request rechecks the authenticated session under the account lock. Password-reset issuance, password changes, factor changes, and account disable/enable invalidate pending changes through a security version. Confirmation revokes sessions, their edit locks, outstanding reset tokens, and pending login challenges. Expired address reservations cannot prevent a different account from requesting that address. Legacy copyable invitations are not mailbox proof: with SMTP enabled they must first be resent with a rotated token.

Durable queue admission serializes recipient/template and actor limits: five messages per recipient and template per hour, thirty per triggering person per hour, and at least sixty seconds between resends. Verification links, including operator bulk issuance, have their own thirty-per-hour person budget so they cannot exhaust the person's notices and test mail. Security state changes and their notifications share a transaction. Operator status exposes configuration, last successful delivery, and failed count and the number of suppressed security notices only; test mail always targets the authenticated operator's own address.

A security notice never blocks or rolls back the security action it reports. If the per-recipient notice limit is exhausted, the login, password change, password reset, factor change or address change still commits, no mail is queued, and a terminal `suppressed` row is stored in the same transaction. Suppressed rows carry no token or rendered content, are not counted against the recipient or person windows, are never delivered, and appear only as a count in the operator status (no recipient or content in logs). The earlier design rolled the action back, which let anyone who knew a password sign in five times an hour and thereby block that person's password change, factor setup, reset, address confirmation and further logins; availability of the security action takes precedence over the notice. The per-recipient limit stays so a flood cannot fill the mailbox. For security notices the per-recipient limit is counted per event type, so a flood of new-login notices cannot suppress a later notice about a password change, password reset, factor change or address change. Limits that protect user-triggered mail with a link (invitation, verification, address change, reset issue) are unchanged and still refuse the request.

An address-change request for an address that is already in use performs the same observable work as one for a free address: the old address receives the same notice, and the target address is accounted in the same resend and hourly windows through a terminal, never delivered queue row. The response is identical. Terminal queue rows are purged after seven days by the maintenance job, which keeps the newest successful delivery for the operator status; expired verification tokens and pending address changes are purged there too.

The actor UUID in the queue is provenance, without a user foreign key: notification admission must not acquire another user's row lock while holding the global admission lock. Operator verification runs in bounded, cursor-based batches and can be continued after its rate-limit cooldown. New browser sessions also generate the new-login notice; session refreshes do not. Existing host-only password-reset recovery continues to print its explicitly protected recovery link because host access is the recovery authority even when mail is unavailable.

## Consequences and alternatives

Migration 0019 adds mail persistence and verification capability state. Existing accounts retain their verification status. SMTP secrets use files and deployment examples must explicitly permit outbound SMTP networking. A development-only test sink proves real SMTP delivery, TLS enforcement, and retry behavior; it is absent from production installation.

Direct synchronous SMTP was rejected because it cannot roll back with database changes and would couple request latency to the mail server. Plaintext queued tokens were rejected because database access would expose live capabilities. Automatically trusting legacy addresses was rejected because it would preserve account squatting. Graph, OAuth, newsletters, inbound mail, and application DKIM remain outside AC-09.

Implementation evidence, dependency versions/licenses, remaining limitations, and executed acceptance checks are recorded in the AC-09 report.

## Ergänzung AC-09b (2026-10-31)

Graph Mail.Send and SMTP XOAUTH2 extend the existing `MailTransport`; queue, schema, templates, and admission limits remain unchanged. Graph uses only the public Microsoft endpoints `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` and `https://graph.microsoft.com/v1.0/users/{sender}/sendMail`. SMTP OAuth providers are `microsoft` and `google`; Microsoft tokens target `https://outlook.office365.com/.default` with `SMTP.SendAsApp`, Google service-account delegation targets `https://mail.google.com/` and uses the configured sender as the delegated subject. OAuth uses rustls-only HTTPS, fixed endpoints, bounded response bodies and timeouts, and redirect refusal. Test-only endpoint/trust overrides accept loopback only.

Credentials remain file-only (`*_FILE`). Graph certificate and key are an exclusive credential mode preferred over a client secret file. SMTP XOAUTH2 uses provider-specific Microsoft tenant/client/certificate/key or secret-file fields, or Google service-account JSON file and delegated sender. Configuration rejects unknown, partial, conflicting, and orphan fields. Access tokens stay in process memory, are reused only with more than five minutes remaining, and are refreshed once after HTTP 401. Retryable provider status and `Retry-After` flow back to the unchanged worker retry scheduler; permanent failures expose only allowlisted provider codes. Arbitrary response bodies are never retained or returned.

Operator status adds active transport, configured sender, certificate expiry when applicable, and a sanitized last provider error code alongside existing delivery counts. Setup follows Microsoft's Entra client-credentials, Exchange Online application RBAC / SMTP registration guidance and Google's service-account domain-wide delegation guidance. Graph `Mail.Send` is tenant-wide unless mailbox access is restricted with Exchange application RBAC or an application access policy.

The recommended Graph setup assigns the scoped Exchange `Application Mail.Send` role without an additional unscoped Entra grant, since those grants are additive. Graph sends the rendered HTML through JSON `sendMail` to honor `saveToSentItems=false`; it does not attach the separately rendered plain-text alternative. SMTP continues to send both alternatives. A custom MIME request was rejected because its sent-items behavior cannot express the configured JSON option with the same confidence.

Transport status is process-local and resets on restart. Provider codes shown to the operator retain their allowlisted spelling; queue failure codes map to the existing lowercase constraint. Delivery is at-least-once for Graph as for SMTP: a network error after the provider accepted a message is retried and can produce a duplicate. Missing release overlays disable mail rather than dropping authentication. Credential reads reject nonregular files and final symlinks/reparse points, enforce bounded reads and Unix file modes, and leave Windows ACL policy to the operator. No new database migration is needed.
