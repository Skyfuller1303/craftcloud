# Threat model (STRIDE / trust boundary review)

## Assets

Benutzeridentitäten, Session-/Device-Tokens, Org-/Workspace-Metadaten, private Entwurfsdateien, Dateiversionen und -Hashes, Einladungen, Audit-Historie, Storage-Buckets, Secrets, Backup-Archive und Restore-Kontrolle. Betreiber mit Root-/DB-/Storagezugriff kann **unverschlüsselte Dateien lesen**; E2EE ist nicht Bestandteil des MVP.

## Attackers

- Anonymer Internetnutzer: Login-/Setup-/Share-Link-Abuse.
- Angemeldeter Viewer: IDOR, Schreib-/Role-Eskalation, fremde Workspace-Listen.
- Eingeladener Externer: Scope-Lateral-Movement.
- Kompromittierter Desktop-Token: Replay/Duration/Scopes.
- Bösartiger File Uploader: Parser-/Zip-Bomb/Path-Traversal/Quota-DoS.
- Fehlkonfigurierter Reverse Proxy: Host-/X-Forwarded-/Cookie-Bypass.
- Storage-Misconfiguration/Operator error: ungeschützte Buckets, Backup-Verlust.

## Desktop-Geräte-Sitzungen (AC-01)

Die zusätzliche Vertrauensgrenze liegt zwischen einem Desktop-Client und der API. Ein Client mit gültigem Bearer-Token erhält nur die aktuellen Rechte des zugehörigen Kontos. Der Launcher darf keine Tokens an Apps weitergeben; Schlüsselbund-Code folgt in AC-04. [ADR-0018](../09-decisions/adr-0018-device-sessions.md) hält die Entscheidung fest.

| Angriff | Schutz | Nachweis |
|---|---|---|
| Gestohlenes Zugriffstoken oder Tokens aus Datenbank/Backup | 256 zufällige Bit, Präfix `ccd_at_`, SHA-256 in der Datenbank, standardmäßig 15 Minuten Gültigkeit, sofortiger Widerruf; Geräte-Sitzungen und Refresh-Historie sind vom Backup ausgeschlossen | Token-Unit-Tests und `crates/craftcloud-api/tests/device.rs` |
| Wiederverwendung oder konkurrierende Erneuerung | Atomare Rotation unter Benutzer-/Sitzungssperre; alte Refresh-Hashes bleiben bis zur Bereinigung erhalten; Wiederverwendung widerruft die ganze Familie mit `refresh_reuse` | Refresh-/Replay-Tests in `device.rs` |
| Account-Enumeration und Passwortversuche | Bestehende Argon2-Prüfung einschließlich Dummy-Hash für unbekannte Adressen und gemeinsame Login-Ratenbegrenzungen | Login- und Rate-Limit-Tests in `device.rs` |
| CSRF über vermischte Cookie-/Bearer-Nachweise | Gemischte Credentials ergeben `400 AMBIGUOUS_CREDENTIALS`; nur explizite Bearer-Anfragen sind von CSRF und Origin ausgenommen; Query-Tokens werden ignoriert | Credential-/CSRF-Tests in `device.rs` |
| HTTP-Downgrade und gefälschte Proxy-Header | Geräte-POST-Routen verlangen TLS außer bei konfiguriertem Loopback; Forwarded-Angaben gelten nur für konfigurierte vertrauenswürdige Proxys | Transporttests in `device.rs` und `device.rs` im API-Quellmodul |
| Widerrufenes Gerät beendet einen laufenden Upload oder behält Rechte | Erneute Sitzungsprüfung unter Organisations-, Benutzer- und Sitzungssperre; transaktionaler Widerruf bei Passwortwechsel, Reset, Deaktivierung, Logout-all und letzter Org-Entfernung | Invalidation-/Upload-Tests in `crates/craftcloud-api/tests/device.rs` |
| Geheimnisse oder personenbezogene Metadaten in Logs/Audit | Ereignisse enthalten feste Aktionscodes und Geräte-IDs; keine Tokens, Passwörter, Namen oder E-Mail-Adressen | Log-/Audit-Test in `device.rs` |

Restrisiken: Ein gestohlenes noch gültiges Token bleibt bis zu Ablauf oder Widerruf verwendbar. Es gibt keine optionale Refresh-Gnadenfrist: Nach einer verlorenen Antwort kann eine erneute Anmeldung nötig sein. TLS schützt nicht vor kompromittierten Clients oder einem kompromittierten Host. Proxy-Logs und Betriebssystem-Schlüsselbund liegen außerhalb dieser Serverimplementierung; TOTP folgt in AC-02. Die Geräte-Namen sind untrusted Anzeigetext und werden bereinigt sowie vom Webpanel als Text gerendert.

## Zwei-Faktor-Anmeldung (AC-02)

[ADR-0019](../09-decisions/adr-0019-two-factor.md) erweitert Browser- und Geräte-Anmeldung um denselben zweiten Faktor. Die bisherigen Hinweise „MFA later“ und „TOTP folgt in AC-02“ sind für diesen Ausbau durch die folgende Entscheidung ersetzt. Die Abnahme einschließlich der tatsächlich ausgeführten Testnamen und Logs steht im AC-02-Abschlussbericht.

| Angriff | Schutzanforderung |
|---|---|
| Datenbankabzug offenbart TOTP-Geheimnisse | Authentifizierte Verschlüsselung mit einem getrennt verwahrten Serverschlüssel; keine Schlüsseldatei im Datenbank-Backup. Wiederherstellungscodes werden nur als gesalzene Hashes gespeichert. |
| Gestohlenes Passwort erzeugt direkt eine Sitzung | Nach Passwortprüfung bei aktivem 2FA ausschließlich Challenge; Sitzung erst nach gültigem zweiten Faktor. Browser- und Geräte-Challenges sind getrennt gebunden. |
| Replay oder parallele Einlösung | Kontozeile, Proof-Verbrauch und Sitzungsausstellung werden transaktional abgesichert. Jeder angenommene Zeitschritt und Wiederherstellungscode wird höchstens einmal verwendet. |
| Verteiltes Raten des zweiten Faktors mit bekanntem Passwort und vielen Adressen | Dauerhafter Fehlerzähler je Konto (TOTP und Wiederherstellungscodes gemeinsam, Browser und Gerät), Sperre nach 100 Fehlversuchen mit unveränderter `INVALID_CREDENTIALS`-Antwort und Audit `auth.two_factor_locked`; Aufhebung nur durch Operator-Reset. Restrisiko: gezielte Kontosperre durch jemanden, der das Passwort kennt. |
| Challenge-Diebstahl, Raten oder unbegrenzte Datenbankbelegung | Zufällige opake Challenge, gehasht gespeichert, fünf Minuten Gültigkeit, höchstens fünf Versuche, Bindung an Konto, Adresse und Anmeldeart sowie bestehende Login-Limits. |
| Passwortwechsel, 2FA-Wechsel oder Reset während der Anmeldung | Alte Challenges und vorab geprüfte Credentials dürfen keine neue Sitzung nach dem Widerruf erzeugen; die finale Entscheidung muss den aktuellen Kontozustand unter Sperre prüfen. |
| Fehlende Schlüsseldatei wird zum 2FA-Bypass | Fehlende oder falsche Schlüssel führen zu einer nicht verfügbaren Funktion, niemals zu Passwort-only-Anmeldung eines bereits eingerichteten Kontos. |
| Grant oder direkter Objektzugriff umgeht Organisationspflicht | Prüfung im serverseitigen Organisationsscope einschließlich AC-03-Grants und Schreibabschluss nach Upload. Andere Organisationen bleiben erreichbar. |
| QR-Dienst, Browser-Speicher oder Telemetrie verrät Geheimnisse | QR-Erzeugung lokal im Browser, unveränderte CSP, Geheimnisse nur im flüchtigen Einrichtungsdialog; keine Codes, Challenge-IDs oder Geheimnisse in Log/Audit. |
| Sicherheitsänderung lässt gestohlene Sitzungen gültig | Aktivierung, Deaktivierung und Reset widerrufen andere Browser- und Geräte-Sitzungen atomar mit der Änderung. |
| Restore reaktiviert alte Faktoren oder Wiederherstellungscodes | Geschützte Schlüsselaufbewahrung und dokumentierte Restore-Probe; nach produktivem Restore Recovery-Codes erneuern und zurückgesetzte Faktoren überprüfen. |

Restrisiken: TOTP schützt nicht gegen Phishing mit sofortiger Weiterleitung oder einen kompromittierten Client. Ein Angreifer mit Zugriff auf Datenbank und Schlüsseldatei kann Geheimnisse entschlüsseln. Die bestehende Ratenbegrenzung ist pro Serverprozess; eine horizontale Verteilung benötigt eine gemeinsame Begrenzung (der Fehlerzähler je Konto ist dagegen in der Datenbank und gilt prozessübergreifend). Organisationsrouten werden anhand des Pfads erkannt: nicht decodierbare Segmente gelten als ohne Organisation (der Router lehnt sie ab), Instanz-Admin-Pfade unter `/api/v1/admin/` unterliegen der Organisationspflicht nicht. Ein legitimer Wechsel der Client-Adresse während des Anmeldeschritts kann einen Neustart der Anmeldung erfordern. Passkeys sind nicht Bestandteil von AC-02.

## FigCraft-Live (AC-06)

Der optionale Begleitdienst bildet eine zusätzliche Vertrauensgrenze. Sein Verwaltungsschlüssel kann alle gehosteten Dateien verändern; nur der CraftCloud-Prozess und FigCraft erhalten die geschützte Schlüsseldatei. Das interne Netz hat keinen veröffentlichten FigCraft-Port. Der öffentliche Caddy-Pfad verwendet WSS; Open-Publish ist ausgeschaltet. Ein kompromittierter Host oder ein kompromittierter FigCraft-Dienst liegt weiterhin innerhalb dieser Vertrauensgrenze und kann Dokumente lesen oder verändern. Native Dokumente sind auf dem Begleitdienst nicht Ende-zu-Ende-verschlüsselt.

Ein persönlicher Link ist ein Bearer-Geheimnis: Die Datenbank ordnet ihn einer Person zu, FigCraft prüft beim Join aber nur Token und Zugriffsart. Weitergabe überträgt Zugriff bis zum Widerruf. Tokens werden mit dem AC-02-Schlüssel verschlüsselt gespeichert, an Datei, Person und Zugriffsart gebunden und weder in Audit noch in Logs aufgenommen. Der Webdialog hält sie ausschließlich im Arbeitsspeicher und öffnet nur das erwartete `figcraft://join`-Schema. Browser-Erweiterungen, Bildschirmaufnahmen, Zwischenablage und ein bewusst weitergereichter Link bleiben außerhalb dieses Schutzes.

Jede API-Aktion prüft die zentrale Policy; Ausgabe oder Persistierung nach einem externen Aufruf prüft erneut die aktuellen Rechte. Organisationstransaktionen und eine Sperre je Datei schützen gegen Veröffentlichung, Linkerneuerung und Rechteentzug im Rennen. Rechteänderungen schreiben einen dauerhaften Widerrufsauftrag atomar mit der Änderung. Worker und zusätzlicher Abgleich widerrufen überschüssige Links. Bei Netzpartition oder ausgefallenem FigCraft ist sofortiger Widerruf nicht garantierbar; ein bereits verbundener Client kann bis zur Wiederherstellung weiterarbeiten. Diese Grenze muss bei besonders sensiblen Dateien in die Betriebsentscheidung eingehen.

Automatische Sicherungen verwenden einen eigenen, an die konkrete aktive Live-Datei gebundenen Policy-Akteur. Er kann ausschließlich die benötigten Lese-, Upload- und Versionsaktionen ausführen; er besitzt keine Sitzung und keine allgemeinen Administratorrechte. Publisher-Identität im Versionsdatensatz ist Herkunft, keine behauptete interaktive Handlung. Audit und `actor_kind = figcraft_live` kennzeichnen den Systemvorgang. Normale Uploads und Versions-Restore dürfen den Live-Stand nicht nebenläufig überschreiben. Beenden widerruft zuerst die persönlichen Verbindungen, sichert danach den endgültigen Stand und löscht die entfernte Datei erst nach bestätigter Sicherung.

Der Adapter nimmt höchstens 64 MiB an, begrenzt Nachrichten und Verbindungen und bricht Netzwerkoperationen nach einer absoluten Frist ab. Er lehnt Archive mit Reparaturbedarf ab und erhält nicht synchronisierte Archivteile aus der ursprünglichen Version. Temporäre Exportlinks sind nach einem fehlgeschlagenen Widerruf wiederauffindbar. Unbekannte zukünftige FigCraft-Archivbestandteile sind kein zugesicherter kompatibler Import; der Commit ist deshalb exakt gepinnt.

Ein Restore widerruft Datenbank-Links und verlangt eine neue Veröffentlichung. Er kann keine alte externe FigCraft-Instanz abschalten. Das Runbook verlangt daher einen isolierten alten Dienst und ein frisches Datenvolume; andernfalls bleiben alte Links außerhalb der wiederhergestellten Berechtigungsautorität verwendbar. Native Capability-Prüfung, gemeinsame Konten und CraftHub-Protokoll v3 sind nicht Bestandteil von AC-06.

## High-priority abuse cases

1. `/setup/complete` race creates two owners. *Mitigation (PR-004):* the setup transaction claims the singleton row `instance_setup` first, so concurrent attempts serialize on its primary key; tests `twenty_concurrent_requests_create_exactly_one_operator` (HTTP, 20 requests, exactly one 201) and `concurrent_setups_produce_exactly_one_winner` (DB), rollback in `failure_inside_the_transaction_leaves_nothing_behind` and `setup_failure_rolls_back_everything`; wrong token and token-free probing in `setup_flow_status_wrong_token_success_and_repeat` and `wrong_token_is_forbidden_and_never_logged`.
2. User A manipulates `workspace_id` of User B and obtains same-name file. *Mitigation (PR-006, organizations level):* repository scopes only come from policy permits, non-members get an identical 404; tests `a_member_of_one_organization_sees_nothing_of_another` (all org routes, unknown-id comparison, operator, swapped ids), `plain_members_cannot_write_and_non_members_do_not_exist_for_them`, `admins_manage_members_and_admins_but_never_touch_owners`, `concurrent_demotions_and_departures_never_leave_an_organization_without_an_owner`, `every_unsafe_route_needs_a_session_the_csrf_header_and_the_origin`.
3. A Viewer starts upload then role revoked before commit.
4. A stale signed URL continues working after explicit revoke.
5. Storage key constructed from `../../etc/passwd`.
6. Upload reservation bypasses quota with 10 parallel sessions.
7. Raw `Authorization` logged via tracing middleware.
8. Browser CSRF deletes a project. *Mitigation (PR-005):* every unsafe session request needs the CSRF header and a same-origin `Origin`; tests `csrf_header_and_origin_are_both_required_for_unsafe_methods`, `login_rejects_foreign_origins_and_cross_site_fetches`. Further session/auth tests: `invalid_sessions_are_401`, `idle_timeout_expires_sessions_and_activity_extends_them`, `absolute_timeout_ends_sessions_despite_activity`, `logout_revokes_the_session_and_logout_all_revokes_every_session_of_the_user`, `password_change_requires_the_current_password_and_revokes_other_sessions`, `password_reset_link_is_operator_only_single_use_and_expires`, `every_login_failure_looks_identical`, `account_rate_limit_is_per_email_and_returns_retry_after`, `secrets_never_reach_the_logs`, `only_failed_logins_count_and_block_per_account_and_address`, `flooding_with_fresh_addresses_cannot_evict_an_active_account_counter`, `ipv6_addresses_in_one_64_prefix_share_limits`, `verified_login_insert_waits_for_a_password_change_in_flight_and_then_refuses`, `issuing_a_link_revokes_the_sessions_of_that_account_immediately`.
9. Reverse proxy trusts arbitrary `X-Forwarded-Host` to send invite tokens to attacker domain. *Mitigation (PR-005/PR-007):* invitation and reset links are built only from the configured `CRAFTCLOUD_PUBLIC_URL`, never from `Host` or `X-Forwarded-*`; without a configured URL the route answers 503 `AUTH_UNAVAILABLE`. Tests: `who_may_invite_what` (link prefix `https://cloud.test/invite#token=`).
10. Backup/restore replaces secrets or tenant pointers with inconsistent versions.

## Backup and restore abuse cases (PR-019, CC-F14, CC-P03-08)

`craftcloud-server admin backup create | verify | restore` runs on the host with the database secret; there is no HTTP route for it, so every case below starts with host, volume or backup-medium access. Tests are in `crates/craftcloud-api/tests/backup.rs` (`cargo xtask db-test`), `crates/craftcloud-backup` (unit tests) and `apps/craftcloud-server/tests/cli.rs`.

| Abuse case | Mitigation | Test |
|---|---|---|
| A stolen or leaked backup exposes password hashes, e-mail addresses, the audit log and every file | the directory is written with mode 0700/0600 (unix), the manifest holds no credentials, names or addresses, sessions and password reset tokens are not in the backup, the runbook requires encryption before the copy leaves the host (`age`/`gpg` example) and key custody apart from the backup; **encryption is not implemented** and left to the operator | manifest does not contain the database URL, its password or an address; modes on unix (the unix mode assertions are not run on the Windows development host) |
| A backup is altered or damaged in transit or on the medium (table file, blob, blob list, manifest, extra or missing files) | SHA-256 and size per table file and blob, row count, blob list checksum, ordered unique keys, exact file inventory (extra files, links and directories are rejected), checksum of the manifest in `manifest.sha256`, optional pinning of the manifest digest (`--manifest-sha256`, printed by `create`) taken from a separate place; `restore` verifies everything before it writes anything | tampered table, tampered, enlarged and missing blob, extra file and directory, forged manifest, wrong digest, malformed checksum file |
| An attacker who can write the backup medium forges a backup with matching checksums (for example to plant an operator account) | **not prevented by the checksum file** (it sits next to the manifest); the pinned manifest digest kept elsewhere detects it, and restore only ever loads into an empty instance, so a forged backup cannot change a running one; restore backups only from a medium and a digest you trust. No signature | forged manifest with a recomputed checksum file is rejected only for an unknown format or migration version, not for forged content (residual risk); a file swapped between `verify` and the load is caught by the hashes taken while streaming, so a pinned digest cannot be bypassed by a race (see the next row) |
| A restore overwrites or mixes into a live instance | restore refuses a database that has rows in any table, a database with tables but no migration history, a database at another migration version, and a store with any object, temporary file or marker; there is no merge or force mode; the restore holds the maintenance advisory lock for its whole run, so a second restore, a backup or a maintenance run cannot interleave (it fails with `Busy`, or finds a non-empty target, and never removes the first restore's objects); every table file is hashed while it streams into the database and the blob list while it is read, and both are compared with the manifest before the commit and before any table is loaded, so a swap after `verify` fails the restore; the restore is refused unless the connected role owns `audit_events` (the audit insert guard would otherwise rewrite timestamps and counters); the binding row is inserted in the load transaction and the marker file is written just before the commit (removed again if the commit fails), so there is no half-restored state after a commit, and a failed restore leaves no rows, binding, marker or objects (a foreign marker or binding that appeared meanwhile is left alone and makes the restore fail) | restore into the migrated source database, into a store with an object, into a database with a foreign table, a second restore into a restored pair, two concurrent restores into one target, a held lock, a table file and a blob list swapped after verify, a binding row or marker file created during the restore, a runtime-role connection |
| A restored backup revives access that was removed (sessions, reset links, disabled accounts, removed members) | `sessions` and `password_reset_tokens` are not backed up, so every session is invalid and every reset link is gone after a restore; **accounts disabled and members removed after the backup come back**, and passwords are those of the backup time: the runbook tells the operator to re-check accounts and memberships after restoring a production instance | restored instance rejects the old session cookie; login works only with a new session |
| A pending invitation survives the restore, including one that was **revoked after the recovery point** | only the token hash is stored and the invitation keeps its original expiry and its state at the recovery point: an invitation revoked later is valid again until it expires, and a holder of an old link can use it. The runbook tells the operator to review and revoke all open invitations after restoring a production instance; there is no command for that yet (listed in docs/gaps.md) | none specific (rows are compared byte for byte in the drill) |
| Garbage collection or retention purge deletes blobs that the snapshot references while the backup copies them | the backup holds the maintenance advisory lock from before the snapshot to the last copied blob; maintenance runs skip meanwhile; the lock is tied to the database connection, so a crashed backup cannot hold it; every copied blob is checked against the size and SHA-256 in the database, a missing or damaged object aborts the backup without a partial result | maintenance run four times before the snapshot, between snapshot and copy and after the copy of trashed files: all skipped, backup and restore complete; the same job deletes everything once the backup is over; killed connection frees the lock |
| A backup taken during uploads is inconsistent (half-committed versions, bytes missing) | tables and blob list come from one `REPEATABLE READ` snapshot; only `committed` blobs are copied (immutable), unfinished uploads and their reservations are neutralised on restore (sessions `aborted`, staged blobs `orphaned`, `reserved_bytes` reset to the bytes of those orphaned blobs, which the next maintenance run releases when it collects them); a version committed after the snapshot is simply after the recovery point | upload stored but not committed and one announced upload at backup time; a version committed between snapshot and copy |
| A malicious backup directory writes outside the store or exhausts memory | object keys are 32 lowercase hex characters (validated before any path is built), table file names are derived from the fixed table list, symlinks are rejected, the manifest (1 MiB), blob list lines (1 KiB) and counts are bounded, unknown fields are rejected; tables and blobs are streamed in blocks | manifest, blob line and key validation unit tests; oversized manifest and overlong blob list line |
| The backup process is used to read data it should not or runs unattended with excess rights | create and verify need only the runtime role (read on all tables, insert of the audit event); restore needs the owner role and is the only command that creates tables; neither reads secrets other than the database URL file; nothing is printed except counts and the manifest digest; failures and successes are audited (`backup.created`, `backup.restored`) without an actor because host access is the authority | audit event details contain counts only; the CLI output holds no password |
| A restore test with another public URL leaks or reuses the production identity | the database holds no URL; the restored pair gets a new store identity so it cannot be mistaken for the source; the bootstrap token is useless because the setup is restored as completed; secrets are not part of the backup and must be new on the test instance | restored pair has a new marker and `storage_binding` |
| Backups fill the volume, a backup runs for too long and delays maintenance | no space check before writing (the backup aborts and removes its directory when the disk is full); maintenance is postponed while the lock is held and a second backup waits at most 120 s; scheduling and rotation are the operator's job | none (residual risk) |

Residual risks: unencrypted backups on the host volume; no tamper-proof signature; the restore trusts a backup whose digest the operator did not pin; accounts, memberships and invitations changed or revoked after the recovery point reappear in their old state; the audit events written after the recovery point are lost.

## Security gate

No public beta before threat model reviewed by security owner, negative policy suite run, session handling independently reviewed, backup restore demonstrated, admin exposure restricted, transport encrypted, and documented incident reporting. `SECURITY.md` is a draft until official maintainers supply contacts.

## Invitation abuse cases (PR-007, CC-F03)

| Abuse case | Mitigation | Test |
|---|---|---|
| Token guessing or enumeration | 32 random bytes, only the SHA-256 is stored, uniform 400 `INVALID_INVITATION` for unknown, malformed, expired, used and revoked tokens, rate limit per client address | `accepting_creates_the_account_membership_workspace_role_and_a_session`, `accepting_is_rate_limited_per_address_and_invitation_creation_per_user` |
| Replay or double acceptance, also in parallel | single consume `UPDATE ... WHERE accepted_at IS NULL AND revoked_at IS NULL AND expires_at > now`, locked transaction; exactly one account and one membership | `concurrent_accepts_of_one_token_have_exactly_one_winner` |
| Link leaks through logs, referrers or proxies | token in the URL fragment (never sent to servers), accepted only in the request body, never logged; audit lines carry ids only | `tokens_and_addresses_never_reach_the_logs` |
| Stolen link used with another account | an existing account must be logged in as exactly the invited address (403 `INVITATION_EMAIL_MISMATCH`, anonymous 401 `LOGIN_REQUIRED`); link possession alone creates accounts only for addresses without account | `invitations_for_existing_accounts_need_that_account_logged_in` |
| Privilege escalation through invitations | nobody invites `owner`; workspace admins only `member`, own workspace, at most `editor`, only if enabled; the inviter's rights are re-evaluated at acceptance; a demoted inviter's links die | `who_may_invite_what`, `stale_invitations_of_demoted_or_disabled_inviters_and_changed_settings_are_refused` |
| Existing member upgrades their role through an invitation | organization role never changes, workspace role never lowered; org-only invitation for a member: 409 and stays open | `existing_members_keep_their_roles_and_workspace_roles_are_never_lowered` |
| Spam or mailbox flooding, invitation table growth | one open invitation per organization and address (409 `INVITATION_PENDING`, also under concurrency), 1000 open invitations per organization, creation rate limit per user, no e-mail is sent in this phase | `one_open_invitation_per_address_listing_revocation_and_expiry`, `concurrent_invitations_for_one_address_yield_exactly_one` |
| Cross-tenant invitation (workspace of another organization, IDOR) | composite foreign key `(org_id, workspace_id)`, workspace looked up inside the locked organization, 404 otherwise | `who_may_invite_what`, `workspaces_never_cross_organizations_and_swapped_ids_find_nothing` |
| Login CSRF through the anonymous accept route | Origin check as for login; with a cookie also the CSRF header | `every_unsafe_workspace_and_invitation_route_needs_session_csrf_and_origin`, `accepting_creates_the_account_membership_workspace_role_and_a_session` |
| Open (unverified) address claim | link possession is the proof until SMTP verification exists (ADR-0013); documented gap, links are short-lived (72 h), single use and revocable | see docs/gaps.md |

### Account squatting through invitations (residual risk, PR-007)

Until e-mail verification exists, link possession is the proof of an address (ADR-0013). An inviter who accepts their own link creates an instance-wide account for an address they may not own. The real owner of the address who is invited later by another organization receives `LOGIN_REQUIRED` (the account exists) and cannot take it over. This is a documented residual risk, not a fixed one; the full fix is e-mail verification and delivery.

| Aspect | Handling | Test |
|---|---|---|
| Provenance | `users.email_verified_at` stays NULL for every account (also the setup operator) and `users.created_via_invitation_id` records the invitation; origin organization and inviter stay derivable | `invitation_created_accounts_record_provenance_and_the_operator_can_list_them` |
| Detection | `GET /admin/users` (operator only, filter `?unverified=true`) lists accounts with origin; audit line `account.created_via_invitation` with account, invitation, organization and inviter ids | same test |

## Object storage abuse cases (PR-009, CC-F09)

| Abuse case | Mitigation | Test |
|---|---|---|

Out of the threat model: an attacker with write access to the storage directory on the host (who could swap a directory for a link between a check and an open, or read the data directly). | Existence oracle for foreign ids through object-specific errors (SR-03, CC-P03-09) | the syntax of body fields is checked before any object is looked up (`POST /files/{id}/versions` with a malformed `upload_id` answers 422 for every file id); every other validation, precondition, conflict and operational error follows the policy check on the resolved object, so foreign and unknown ids get the same status, code, message and headers | `foreign_and_unknown_objects_answer_identically_on_every_route` (all organization, workspace, project, file, version, upload, member, invitation, quota and audit routes, three header variants, valid and invalid bodies) |
| Other workspace members hijacking a session | only the creator sends content; managers may read and abort | `upload_role_matrix_for_all_four_routes` |

The per-user cap is serialized with a lock on the user row, and a cross-organization race on one `Idempotency-Key` is a 409 (`idempotency_keys_and_the_per_user_cap_hold_across_organizations`). Lock order of an upload creation: organization row, user row, workspace row.

| Concrete ids or tokens in paths end up in logs and metric labels | only the matched route template is used, looked up in the fixed route table (a client cannot create a new label value); query strings and fragments are dropped | same, `metrics_count_requests_by_template_and_never_by_id_or_path` |
| Metrics expose tenants (user or organization ids as labels) or are scraped by anyone | no id of any kind is a label; `/metrics` is never served on the public listener (404 there, also for the operator) but on a separate listener that is off by default, bound to loopback unless `CRAFTCLOUD_METRICS_TOKEN_FILE` is set (a non-loopback address without a token refuses to start); with a token every scrape needs `Authorization: Bearer` (constant-time comparison on a digest, 401 without a body otherwise) | `metrics_are_not_served_on_the_public_listener`, `the_metrics_listener_needs_the_bearer_token_when_one_is_configured`, `metrics_listener_settings_are_validated_before_anything_starts` |
| The readiness endpoint leaks topology or becomes an enumeration oracle | the public answer is `ready`, `degraded` or `NOT_READY` with the common error shape: no component names, versions, counts, hostnames or error texts; the detailed view needs the operator session (`HealthRead`, 403 for everybody else, denial audited) | `ready_answers_ready_with_a_body_that_has_no_details`, `ready_is_503_when_the_database_is_unreachable_and_live_stays_200`, `the_operator_health_view_is_operator_only` |
| Probe traffic loads the database or the disk, or a flood of probes starves real requests | the check runs as one detached task: overlapping probes wait for it, the verdict is cached for 3 s and also stored when every caller gives up, so cancelled probes cannot multiply checks; every dependency check has a 1.5 s timeout and the whole check a 4 s deadline; the probe file is created, read and removed inside one blocking job with a drop guard, and the maintenance run sweeps leftovers older than an hour; the readiness check writes one tiny file in the store's `tmp` directory and removes it | `the_readiness_verdict_is_cached_for_a_moment`, `cancelled_callers_cannot_multiply_readiness_checks` |
| A transient database outage restarts the process in a loop | liveness checks nothing; only readiness depends on the database | `ready_is_503_when_the_database_is_unreachable_and_live_stays_200`, `readiness_turns_503_while_the_server_drains_and_liveness_stays_200` |
| A restored database or store is served as healthy | an epoch conflict makes readiness answer `degraded` (not silently `ready`) and shows up in the operator view and in `craftcloud_storage_epoch_conflict`; a store that cannot be written makes readiness fail; a store refused because it belongs to another database is `degraded` (only file routes answer 503) | `an_epoch_conflict_is_degraded_but_still_ready`, `ready_is_503_when_the_store_cannot_be_written`, `a_store_that_belongs_to_another_database_is_degraded_not_unready` |
| Silent loss of audit events goes unnoticed | the best-effort drop counters (lossy and important) are shown in the operator view and as `craftcloud_audit_events_dropped_total` | `the_operator_view_counts_dropped_audit_events` |
| Log or metric cardinality and size attacks (random paths, methods, request ids) | route and method labels come from closed sets (unknown methods are `OTHER`); the request id is only a log field, never a label; client-supplied ids are length- and character-limited as before | unit tests in `observe.rs`, `the_router_serves_exactly_the_listed_methods_and_nothing_else` |
| Residual risk | the metrics token is a shared bearer secret on an internal network (no TLS on that listener; terminate or tunnel it if the scraper is on another host); free disk space is measured by running `df` (fixed arguments, no user input) and is absent without it; an operator with host access sees everything the process sees; reverse proxy access logs are outside this server and may hold query strings and headers (see the deployment guide) | |

## Container and proxy abuse cases (PR-018, CC-F14 prerequisites, CC-P03-07)

The Compose stack in `deploy/compose` runs the server behind Caddy. Nothing here replaces host hardening, and the checks below were made by hand against the running stack (Docker Desktop, WSL2), not by an automated test suite, unless a test name is given.

| Abuse case | Mitigation | Test |
|---|---|---|
| A compromised server process writes to the image, escalates to root or uses kernel capabilities | the image is distroless (no shell, no package manager), the server runs as uid 65532 with `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges`, memory and process limits; only the `store` volume and a `noexec` tmpfs are writable | `docker inspect` of the running stack (user, read-only flag, capabilities), upload to the store works |
| A compromised proxy or server reaches the database or the internet | the networks `frontend` and `backend` are `internal` (no outbound route); Caddy is not on `backend`, the database publishes no port; only the proxy network is a trusted proxy | `nc` from the Caddy container to `db:5432` fails, `server:8080` works |
| The server leaks or can read secrets that it does not need | secrets reach containers only as files, not in the Compose file and not in container environments, with one exception: the PostgreSQL entrypoint exports `POSTGRES_PASSWORD` into the database process environment, so the superuser password is readable there by root (in the container or on the host); the database URLs are derived from the role passwords inside `secrets-init`, whose files are replaced in place so running containers keep their mounts; every service mounts only its own subdirectory read-only, 0400, owned by its user; the server gets the runtime database URL only, the owner URL exists only in the one-shot `migrate`; the bootstrap token is mounted only with `compose.setup.yaml` and removed from the volume by the next `up`; `.env`, `secrets/` and keys are in `.gitignore` and `.dockerignore` | listing of the `secrets` volume, `docker inspect` environment, second `up` without the setup file |
| A stolen runtime database credential deletes or alters the audit log | two roles: `craftcloud_owner` owns everything and is used by `migrate` only; the server connects as `craftcloud_runtime` (no superuser, no membership, no owner), `migrate` verifies and grants data rights only (see Audit log abuse cases) | `psql` role query and the `migrate` output of the stack |
| Large uploads are cut or buffered by the proxy, or a slow client holds proxy memory | no request body limit and no request buffering in Caddy (`flush_interval -1` for responses), the server enforces declared size, quota, stall and rate limits | 24 MiB upload and download with equal SHA-256 through Caddy |
| Proxy forwards `/metrics`, caches file bytes, or doubles or removes the server's security headers | `/metrics` is answered with 404 at the proxy and lives on an unpublished listener (it binds `0.0.0.0` in the container, so it is also reachable from Caddy over `frontend`; the bearer token is still required); the proxy sets HSTS only in `acme` mode (none with the internal test CA) and fills in `X-Content-Type-Options` and `Referrer-Policy` when absent, removes `Server`; the server's `Cache-Control: no-store` and CSP pass through unchanged | response headers of `/admin/` and of a download |
| A client spoofs `X-Forwarded-For` or the `Host` to bypass rate limits or poison links | Caddy overwrites forwarded headers from untrusted clients; the server trusts only the `frontend` subnet and builds links from `CRAFTCLOUD_PUBLIC_URL` | covered by the existing `ClientIp` tests; not repeated against the stack |
| Cross-site requests with an `http://` or foreign origin | the public URL is `https://...`; the `__Host-` cookie is `Secure`; foreign and `http://` origins answer 403 | login and mutation with both origins against the stack |
| A broken or compromised image reaches production by a moving tag | all base images are pinned by digest; `npm ci --ignore-scripts` and `cargo build --locked` | review of the Dockerfile |
| Healthcheck endpoint becomes an attack surface or breaks in a read-only image | `craftcloud-server healthcheck` connects only to the own listener, sends one fixed request, reads at most 256 bytes, has 3 s timeouts and reads no configuration or secrets | `healthcheck::tests` (`target_defaults_to_the_server_default_and_maps_unspecified_to_loopback`, `only_a_200_status_line_counts_as_ready`, `run_requests_the_ready_route_and_accepts_200`, `run_fails_on_503_and_on_a_closed_port`) |
| All clients appear as one address behind the Docker userland proxy | none in the template: behind Docker Desktop's proxy (and the IPv6 `docker-proxy` on Linux) Caddy sees the gateway address, so clients share one login and rate-limit bucket and one client can lock out the others; use Linux with `userland-proxy: false` (IPv4 DNAT keeps the address) or host networking for Caddy | not tested; see docs/gaps.md |
| Residual risk | `secrets-init` runs as root without network and is not read-only, and the `secrets` volume holds plain secret files on the Docker host (an operator with Docker access reads everything); Caddy runs as root inside its container (official image) with `NET_BIND_SERVICE` only; PostgreSQL needs five capabilities for its entrypoint; the database connection inside the internal network is not encrypted; Caddy's admin API listens on loopback inside its container; a host with a public ACME certificate needs the CA data volume backed up; no image scan, SBOM or signature was made; Linux-host behaviour was not tested | see docs/gaps.md |

## Admin UI abuse cases (PR-014, CC-F12, CC-P03-01/02)

The browser UI is a static single-page app served by `craftcloud-server` under `/admin` on the same origin as the API (ADR-0015). It has no trusted policy role: every request is authorized by the API again.

| Abuse case | Mitigation | Test |
|---|---|---|
| Path traversal or reading files outside the UI directory through `/admin/...` (`..`, encoded `%2e%2e`, `%2f`, backslash, absolute paths, drive letters, NUL, Windows device names) | the directory is read into memory once at startup and only exact loaded names are served, so no file system path is built from a request; requested paths are decoded once and every segment is checked; unsafe segments are 404 | `path_traversal_and_odd_paths_never_leave_the_snapshot`, `the_snapshot_is_served_from_memory`, `path_parsing` |
| Symbolic links or junctions in the UI directory expose other files | loading refuses links that leave the directory and directory links (startup fails with exit 2) | `loading_refuses_links_that_leave_the_directory`, `a_link_inside_the_directory_is_served_as_a_copy` |
| Oversized or hostile UI directory exhausts memory or the start | limits of 10000 files, 16 MiB per file, 64 MiB in total; violations are a configuration error (exit 2) before the database or any socket is touched | `load_refuses_unusable_directories_and_oversized_content`, `bad_admin_dir_exits_2_before_anything_else_is_touched` |
| Stored or reflected XSS in the admin UI executes script with the session | React escapes all values; strict CSP on every `/admin` answer (`default-src 'self'`, no inline script or style, no `unsafe-eval`, `frame-ancestors 'none'`, `base-uri 'none'`), `nosniff`, no framing; no `dangerouslySetInnerHTML`; the inline style that React Aria would inject is replaced by a stylesheet rule so the CSP can stay strict | `serves_index_assets_and_static_files_with_strict_headers`, `only_get_and_head_and_redirects`; real-browser run without CSP violations (screenshots in the PR-014 evidence) |
| Stale or poisoned caching of the UI | hashed assets are `immutable`, `index.html` and everything else `no-store`; the API's request-context layers do not override this | `serves_index_assets_and_static_files_with_strict_headers` |
| Missing file with an extension answers HTML (script served as page) or a path outside `/admin` falls back to the UI | fallback only for extensionless paths below `/admin`; stale assets are 404 | `spa_fallback_only_for_extensionless_paths_under_admin` |
| Open redirect through `/invite` | fixed targets (`/admin/`, `/admin/invite`), no request data in `Location` | `only_get_and_head_and_redirects` |
| Invitation token leaks through the URL, history, Referer or logs | the token only lives in the URL fragment (never sent to a server); the UI reads it once, replaces the address with `/admin/` immediately and keeps it in memory only; `Referrer-Policy: same-origin`; `/invite` redirects without the fragment being visible to the server | `reads the token from the fragment and removes it from the address` (`src/App.test.tsx`), `creates an account for a new address and continues in the joined organization` |
| CSRF token or credentials persist in the browser | the CSRF token lives in memory of the page only and is fetched again from `GET /auth/session` after a reload; only language and theme are stored in `localStorage`; passwords are cleared from state after every attempt; session cookie is `HttpOnly` | `keeps the token in memory only`, `logs in and stores no secret in browser storage` (`src/api/client.test.ts`, `src/App.test.tsx`) |
| Clickjacking of the login or admin screens | `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every `/admin` answer | `serves_index_assets_and_static_files_with_strict_headers` |
| Malicious npm dependency in the UI build | exact versions, committed lockfile, `npm ci --ignore-scripts`, versions at least two weeks old, `npm audit` (runtime dependencies: 0 findings at PR time) | `cargo xtask web` |

### Additional abuse cases of the dashboard views (PR-015, CC-P03-03/04)

| Abuse case | Mitigation | Test |
|---|---|---|
| UI offers an action the viewer must not do and the user relies on it | the UI only hides or disables controls from the same rules as the permission matrix (`src/permissions.ts`); every request is authorized by the API again, and a 403/404 after a role change is shown inside the dialog with a reload action | `permissions.test.ts`, `shows the server's 403 inside the dialog and reloads on request` |
| One-time invitation link leaks (storage, URL, history, list responses) | the link lives only in component state, is never written to `localStorage`/`sessionStorage`/URL, disappears on dismiss or when the view is left, and the invitation list never contains links or tokens | `creates an invitation, shows the one-time link with a copy button and never stores it` |
| Reset token leaks through URL, history or Referer | read from the fragment and replaced with `/admin/` before the first request; sent only in the JSON body; `/reset-password` redirects without the fragment being visible to the server | `takes the token from the fragment and replaces the address before anything else`, `only_get_and_head_and_redirects` |
| Lost update when two people save the same file | the commit sends `If-Match: "version:<head>"` (or `If-None-Match: *`); 412 `VERSION_CONFLICT` opens a dialog (keep both, overwrite on top of `details.current_version_id`, cancel which aborts the stored upload) and never silently overwrites | `conflict on a new version (412 VERSION_CONFLICT)` |
| Memory exhaustion or blob in page memory through big files | the file is hashed in 4 MiB chunks, sent as a `Blob` body of one `PUT` and downloaded through a plain link; nothing is read completely into memory | `hashes a blob in chunks`, `uploads a new file ...` (request body is the `File` itself) |
| Double submit or replay of an upload reservation | one in-flight action per control; the reservation carries an `Idempotency-Key` that is reused only while the session was not used, a failed body needs a new session | `reuses the idempotency key when only the reservation failed`, `retries after a network error with a fresh session ...` |
| Hostile file names (bidi, control characters, long names) in lists | React escapes all values; names are shown as text only and are never used as paths (downloads use the server's sanitized `Content-Disposition`); the conflict copy name is shortened to 255 bytes | `keeps the copy name within 255 bytes ...` |
| Rate-limit hammering by retry buttons | `Retry-After` countdown keeps the retry control disabled; no automatic retries of unsafe requests | `counts down Retry-After, keeps retry disabled until zero and announces the end` |

Residual risks: the UI directory is trusted build output (whoever writes it controls the UI); the UI and the API share an origin, so an XSS in the UI would be an XSS against the API session; colour contrast and assistive-technology behaviour are not verified in real browsers (docs/gaps.md).
