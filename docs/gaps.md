# Ranked gaps — documentation-first RFC

## Blocking decisions

1. `craftrules` inaccessible via public GitHub; confirm shared standards.
2. Official repository/name and licensing consent absent.
3. Identity provider strategy and role matrix not reviewed.
4. No locked API specification or database schema agreed with integration maintainers.

## Implementation gaps (in recommended order)

5. Secure bootstrap and HTTP skeleton. *PR-004: one-shot operator bootstrap via secret file implemented (no login/session, no CLI recovery yet).* *PR-001 skeleton: health + info only* (no bootstrap, auth, DB or storage). PR-002 added typed env configuration, secret-file loader, trusted-proxy handling and JSON errors for 413/503.
6. Tenant database, policy, Auth/session and invitations. *PR-005: password login, server-side cookie sessions, CSRF, rate limiting and password reset links implemented; policy engine, account disable API and invitations still open; device list implemented. PR-006: organizations, memberships, RBAC policy engine and account disabling implemented; workspace routes, invitations (PR-007) and organization deletion/soft-delete with export path still open.* *PR-007: workspaces, workspace members and link invitations (72 h, single use, revocable, inviter re-checked at acceptance) implemented. Still open: workspace and organization deletion/soft-delete with export path, e-mail delivery and address verification (link possession is the proof until SMTP exists), invitation resend, a browser page for `/invite`, and cleanup of old closed invitation rows. Email verification is needed before multi-tenant production use: until then an inviter can accept their own link and squat an address (residual risk; the operator can list accounts with origin and disable them, see threat model).* *PR-003: PostgreSQL schema (users, organizations, workspaces and memberships), forward-only migrations, tenant-scoped workspace repository; no policy engine, auth, sessions or invitations yet.*
7. Project/file metadata and streaming storage with checksums. *PR-012: retention purge, version retention, two-phase blob garbage collection, reconciliation, verification and usage drift correction implemented as a maintenance job (in-process loop plus `craftcloud-server admin maintenance --once`); this closes the cleanup, deletion and verification items named below. Safety rails added in the PR-012 review: store binding (database identity plus marker file), quarantine instead of deletion for strays, reconciliation brake, clock check against the database, per-item error isolation. Still open: the memory of failed items (excluded for 24 hours) is per process, so a restart retries them at once, `storage-bind --force` and `CRAFTCLOUD_MAINTENANCE_ENABLED` trust the operator's judgement, the first-use binding race of two simultaneously starting servers resolves by a mismatch on one of them until the next start, no lease for running downloads (on Windows an object that a download holds open cannot be deleted and the blob stays `deleting` until a later run succeeds; on unix the download keeps reading the unlinked file), the reconciliation cursor lives in process memory, the version retention and usage drift scans walk the organizations in windows of 50 per run (cursor in process memory) but each window still scans all versions/blobs of its organizations, upload session rows are only removed with their file or version (an open-ended history of aborted or expired sessions remains), the job needs real-world timing with large stores, crash-kill tests of the server process exist since PR-013 (`apps/craftcloud-server/tests/crash.rs`; `abort()` at four named points) but only on the Windows development host: the unix signal path (SIGABRT, `fsync` and directory-sync durability after a real power loss) is untested, an abort is not a power cut (the operating system still flushes written pages, so missing `fsync` calls would not show), and real disk-full (ENOSPC) is only covered by fault injection (507 answer, no leftovers), not by a full volume, purged data stays in backups until they expire, a missing object of a committed blob is only reported (`missing_objects`; no automatic repair), no metrics endpoint for the maintenance job beyond `GET /api/v1/admin/maintenance` (CC-F15).* *PR-011: immutable versions, compare-and-set commit (412 with the current head), restore, version listing, download with ACL re-check, single byte ranges and integrity checking implemented. Still open: retention and deletion of old versions and blobs (old versions are kept; CC-P02-06), periodic verification of stored blobs (a corrupt blob is only discovered by a full download and then marked `corrupt`; CC-P02-07), multi-range responses, a cap of concurrent downloads, resumable uploads; the verification job (CC-P02-07) must also re-check blobs marked `corrupt` and set them back to `committed` when the object verifies again (a transient failure or a restored backup).* *PR-010: upload sessions, streamed content with SHA-256 verification, quota reservation and usage endpoints implemented (staged, uncommitted blobs). Still open: version commit and download (CC-P02-04/05), resumable uploads, cleanup of orphaned blobs and expired sessions as a job (the functions `expire_due_all` and `orphaned_blobs` exist), release of committed bytes when versions are deleted, per-IP/user rate limits for uploads beyond the open-session caps; the reconciliation job (CC-P02-07) must also remove objects that have no `blobs` row and are older than a grace period (a crash between publishing and recording leaves one).* *PR-009: local filesystem object store (`craftcloud-storage`) with streamed writes, byte limits, SHA-256, atomic publish, range reads, listing for reconciliation and fault injection implemented; no HTTP routes yet. Still open: upload/download routes, S3 adapter, resumable uploads, reconciliation job, real disk-full tests on a small volume (needs admin rights), symlink tests on Windows (need privilege), reconciliation (CC-P02-07) must delete unreferenced objects older than a grace period and stale `.part` files, because a cancelled publish can leave an unreferenced object or temp file, unix-only paths untested on the Windows development host.* *PR-008: projects, flat file metadata, soft delete with restore window, safe names and pagination implemented (metadata only). Still open: file content, versions and checksums (CC-F07/F08), storage adapters, purge of expired trash entries and quota accounting (CC-P02-06), folder hierarchy, moving files between projects.*
8. Version commit with CAS, soft delete, retention, quotas.
